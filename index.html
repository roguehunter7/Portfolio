I specialize in architecting secure, automated infrastructure. This site serves as a live case study for a zero-ingress cloud environment, demonstrating the transition from initial resource constraints, serverless migration, and cost optimization.

Phase 1: Bootstrapping

Native Resource Polling

Constraint: The GCP e2-micro instance is limited to 1GB of RAM. Standard CI/CD runners posed a high risk of triggering Out-Of-Memory (OOM) events.

Architecture: A pull-based GitOps loop using systemd.timer and a native Bash script. The system polled the GitHub API every 2 minutes for SHA deltas, minimizing memory overhead.

Phase 2: Refactored

Push-Based IAP Tunneling

Requirement: Transition to an instant, push-based model while maintaining a zero-ingress security posture (no public open ports).

Architecture: Replaced polling with GitHub Actions. Utilized GCP Identity-Aware Proxy (IAP) to securely tunnel SSH deployments via Port 22 without exposing the port to the public internet.

Phase 3: Registry & Telemetry

GHCR & Native systemd

Optimization: Building on the VM caused OOM crashes. Real-time telemetry was constrained inside the docker container network boundaries.

Architecture: Built and pushed unprivileged Nginx image to GHCR in CI. Telemetry daemon runs natively on the host under systemd, proxied via the host bridge.

Phase 4: Serverless

Cloud Run & WIF

Optimization: Managing a VM, Cloudflare tunnels, and OS-level systemd daemons added unnecessary operational overhead.

Architecture: Transitioned to Google Cloud Run (Serverless). Implemented Workload Identity Federation (WIF) for keyless GitHub Actions deployments via Artifact Registry.

Phase 5: Cost Optimization

Zero-Ingress Docker Compose

Constraint: Cloud Run, Artifact Registry, and Firestore accumulated unwanted storage and access costs.

Architecture: Moved back to a free-tier GCE e2-micro VM. Deployed Nginx and Cloudflared in a private Docker Compose stack. Kept WIF for secure push deployments via IAP SSH.

System Architecture Evolution

Current Cost-Optimized VM Architecture (Phase 5)

Our current production environment uses **Terraform** to provision a Zero-Ingress VPC. Deployments are executed by compiling resume PDFs and building containers in GitHub Actions, pushing the package to GHCR, and securely running a push-based SSH deployment over GCP Identity-Aware Proxy (IAP) to run a Docker Compose stack.

The VM Reversion Rationale (Phase 5)

Evaluating Cloud Run Costs

While the serverless architecture in Phase 4 eliminated VM maintenance and cloud tunnels, it introduced unexpected cost vectors. Sustained usage of Artifact Registry storage for hosting multiple Docker image tags, along with Firestore reads/writes from the visitor tracker microservice, accumulated charges. For a low-traffic personal portfolio, these costs represented a step back from our original "100% Free Tier" objective.

The Phase 5 Zero-Ingress Docker Compose Design

To bring our maintenance costs strictly back to $0/month, we retired the Cloud Run and Firestore resources and returned to a single GCP e2-micro VM instance, which is fully covered under the GCP Always Free program.

  • Docker Compose Isolation: Instead of managing Nginx and Cloudflare tunnels directly on the host OS (which previously caused OOM crashes), they run in isolated Docker containers in a unified Docker Compose stack.
  • Zero Exposed Ports: The Nginx frontend exposes no ports to the host VM or the public internet. It resides exclusively on a private Docker bridge network, communicating only with the Cloudflared container which securely tunnels traffic.
  • Public GHCR Packages: Since the codebase is public, we publish our Nginx container to GitHub Container Registry publicly, allowing the VM to pull it anonymously without managing registry secrets.
  • Preserving Security: We retained Workload Identity Federation (WIF) and Identity-Aware Proxy (IAP) SSH tunneling. GitHub Actions keylessly logs in via Port 22 (restricted only to Google's IAP proxy IPs) to execute automated push deployments.

The Result: Zero monthly cost, zero open ports on the VM host, container-isolated networking, and automated keyless push deployments.
