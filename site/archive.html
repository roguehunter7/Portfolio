Phase 1 — Bootstrap & GitOps polling

A hand-deployed VM learns to deploy itself.

May 2026

Why

The project started as a plain static portfolio served from a single cloud VM. Manual re-deploys didn't scale and there was no way to audit what was live. We wanted the site to track the repository without anyone babysitting a deploy, and we needed a repeatable way to route traffic and secure the host.

How

A pull-based GitOps loop polled the repository for changes and re-deployed on delta. Nginx served the site from a Docker image built and pushed earlier. As it hardened, we added HSTS, Docker image CVE remediation, and introduced Terraform to declare the VM and networking.

  • Deploy: pull-based polling loop; Docker + nginx to serve the static site.
  • Hardening: HSTS header, hardened base image, strict firewall posture.
  • IaC: Terraform introduced to describe the cloud resources reproducibly.

Phase 2 — Observability & IaC serverless

Knowing what's happening, then rebuilding the whole thing declaratively.

June 2026

Why

Hand-rolled sidecar scripts gave no real-time signal, and the growing fleet of bespoke shell scripts became unmaintainable. We wanted live observability and a path where the deployment was fully declared in code — and we wanted to prove the whole stack could run serverless.

How

We added an Nginx stub_status/frontend-polling metrics daemon with a systemd service and containerized the resume build (LaTeX compiled in CI). Then we rebuilt the deployment on Terraform + GitHub Actions with a proper migration to Cloud Run + Firestore: a Go visitor-tracker API authenticated via Workload Identity Federation, shipped as a multi-stage image.

  • Observability: stub_status polling + a metrics daemon with chaos injection.
  • Resume: LaTeX compiled in CI and served from the container (later migrated to HTML+CSS — see Phase 4).
  • Serverless: Terraform + Actions; Cloud Run, Firestore, WIF keyless auth, multi-stage Go image.

Phase 3 — No-Open-Ports Docker Compose

The cost of serverless pushed everything back behind a no-public-ports host.

July 2026

Why

Cloud Run + Artifact Registry + Firestore read/write fees accumulated for a low-traffic portfolio, breaking the "$0/month" goal. The lesson was honest: serverless removed VM maintenance but added a cost vector the workload didn't justify. We returned to a single free-tier VM — but this time with a fundamentally more secure posture: no open ports.

How

We removed the tracker API and rebuilt the stack as a Docker Compose project: Nginx and cloudflared containers on an isolated Compose network. All ingress arrives via a Cloudflare Tunnel (outbound connection), so the host exposes no open ports. We pinned the tunnel image, hardened the VM bootstrap and Nginx, added a VM-readiness check to the deploy, and released the project under MIT.

  • Ingress: Cloudflare Tunnel only — no open ports, no host firewall exposure.
  • Runtime: Docker Compose v2, pinned tunnel image, hardened Nginx + VM bootstrapping.
  • Pipeline: VM-readiness check before deploy; images built in CI and pulled anonymously.

Phase 4 — Edge migration to Cloudflare Pages

Static assets move to the edge; the VM stops serving the site.

August 2026

Why

A static resume/portfolio doesn't need an origin server at all. Serving it at the edge is faster, has first-class security-header control, and frees the VM for real work. The deploy also became simpler: render the PDF, publish to Pages — one workflow_dispatch run (deliberately manual, so a push never publishes unreviewed).

How

We migrated the static site to Cloudflare Pages with a _headers policy that hardens HSTS, nosniff, framing and permissions. The resume PDF is rendered by CI (headless Chrome) from the ATS-safe HTML. We made the site AI-friendly with robots.txt, llms.txt, and a JSON-LD Person schema, and documented the HTML-resume rationale.

  • Deploy: wrangler pages deploy site/, idempotent project create.
  • Hardening: HSTS, nosniff, X-Frame-Options, Referrer-Policy, Permissions-Policy, immutable font caching, preview noindex.
  • No CSP (deliberate): a static site with no input, no forms and no third-party origins except the diagram pages' webfont has nothing for a policy to protect — and script-src 'self' would not stop the one plausible attack, since a compromised repo or deploy token can publish a same-origin script. The strict policy's per-route exception broke the resume twice, so it was cut.
  • Content: robots/llms.txt, JSON-LD, CI-rendered ATS-safe resume PDF.
  • Resume pivot: the resume left LaTeX — it's now plain HTML+CSS rendered to PDF by headless Chrome.
  • Diagrams: inline SVG generated with Archify (no client-side renderer, no chart library); each page is self-contained with its own CSS variables, so dark/light theming is a variable swap — the one external request is JetBrains Mono from Google Fonts.

Phase 5 — Repurposing the compute

Freed VMs become an AI host and a dev box with no open ports.

August 2026

Why

Once the site was on Pages, the free-tier VMs were idle capacity. Rather than shut them down, we re-purposed them: first a self-hosted AI assistant, then a browser-accessible development box — both keeping the no-open-ports posture so no port is ever reachable from the internet.

How

We provisioned a Hermes AI-assistant host (outbound-only: Telegram polling + an LLM API, admin via IAP SSH), with a resume.json master data file and DeepSeek backend. Then we built an Oracle Cloud Always-Free A1.Flex dev box provisioned by Terraform + GitHub Actions: a ttyd browser terminal, Node LTS via nvm, a hardened firewall, and cost guardrails (tenancy-wide budget + quota that denies everything except the Always-Free allocation).

  • Hermes host: outbound-only AI assistant, DeepSeek backend, Telegram pairing, IAP SSH admin.
  • Oracle dev box: A1.Flex (2 OCPU / 12 GB), cloudflared tunnel, browser terminal, monthly maintenance.
  • Guardrails: tenancy budget + compute/storage quotas limiting to the Always-Free tier ($0).

Phase 6 — Vaultwarden host

The GCP VM becomes a self-hosted password vault with no open ports.

August 2026

Why

With Hermes relocated to Oracle, the GCP e2-micro was available again. A self-hosted password manager is a great use of free-tier compute, and it must be maximally locked down: a credential store is exactly the workload that demands zero public exposure and least-privilege access.

How

The VM now runs Vaultwarden (single Rust container on loopback :8000 plus a cloudflared container) reached only via the vault.sreeramkr.com tunnel route. Secrets live in a root-owned 0600 .env written by CI, and the Argon2 admin token is interpolated correctly ($ doubled). It runs on a least-privilege service account scoped to one private GCS bucket, with a nightly SQLite backup that prunes to the newest ten. Admin is over IAP SSH; no open ports.

  • No open ports: deny-all firewall + IAP-only SSH; loopback-only :8000.
  • Secrets: 0600 .env via env_file, correct $ escaping.
  • Least privilege: dedicated backup SA (storage.objectUser) on one private bucket; nightly backup + prune to 10.

Phase 7 — Oracle dev box + Hermes

The freed Oracle compute becomes a no-open-ports Ubuntu dev box running Hermes in Docker.

September 2026

Why

The site had moved to the edge and the free-tier compute was idle. Rather than leave it dark, the Oracle A1.Flex became a general-purpose dev box: a browser terminal over the existing Cloudflare Tunnel, with Hermes moved off GCP into a container on the same host. The GCP e2-micro stays the Vaultwarden host (Phase 6).

How

The box runs Ubuntu 24.04 (aarch64) on the Always Free A1.Flex shape, provisioned by Terraform + cloud-init from this repository. ttyd serves a plain bash login shell on loopback :7681; the tunnel points ssh.sreeramkr.com at it and Cloudflare Access gates that route — ttyd itself carries no credential. Node and DSH come from nvm: pnpm, @deepseek-ai/dsh@next, the dsh-tui profile, and the Archify web bundle. Hermes runs from the official nousresearch/hermes-agent image with /opt/hermes mounted at /opt/data; Telegram is long-polled outbound and its gateway API stays on loopback :8642. There is no security group: ufw denies inbound and the OpenSSH server is removed, so no service binds a public interface. Vaultwarden keeps running on the GCP box (Phase 6), loopback :8000 behind its own tunnel. One monthly maintenance pass updates apt, nvm/DSH, and the Hermes image, then reboots.

  • Ingress: outbound Cloudflare Tunnel only; Cloudflare Access in front of the terminal route.
  • Host: A1.Flex 2 OCPU / 12 GB, Ubuntu 24.04; no NSG, ufw deny-inbound, OpenSSH removed.
  • Workloads: ttyd + bash, DSH (tui + web), and Hermes in Docker on loopback.
  • Fleet: the GCP e2-micro stays the Vaultwarden host from Phase 6.

Phase 8 — Consolidation: one workload, snapshot-backed rebuilds (current)

The dev box stops being three ways to reach a shell and becomes a single Hermes host that can rebuild itself.

September 2026 — current

Why

The box carried three overlapping ways in — a browser terminal, the harness's own web UI, and an agent in a container — plus a host toolchain to keep alive. None of that was the point; Hermes was. Every extra service was another listener to patch and another way for the host to fail while the agent was the only thing that mattered. So the question became: what is the smallest host that runs Hermes, and can it be rebuilt from nothing without losing the agent's memory?

How

Everything above the OS changed. Hermes is installed natively as a dedicated hermes user: the official installer brings its own uv-managed Python, Node and ripgrep, so the distro's versions are never in the dependency path and a monthly apt upgrade cannot break the agent. Two systemd units run it — the gateway (Telegram long poll, outbound) and the dashboard on :9119. sshd binds loopback :22; the dashboard listens on all interfaces and keeps its own username/password gate — Hermes only enforces that gate on a non-loopback bind — with ufw dropping inbound connections before they reach it. Both are reached only as SSH or HTTP carried by the Cloudflare Tunnel and gated by Access. Docker, ttyd and the harness are gone, and CI never logs into the box. Agent state lives in /home/hermes/.hermes and is snapshotted every six hours to a private OCI Object Storage bucket using the instance principal, so no key sits on the host. A rebuild is one workflow run with a single reset checkbox: it empties the bucket and destroys the instance for a factory-fresh agent, or keeps the snapshots so the host restores the newest one at first boot. The bucket carries prevent_destroy, so the only copy of the agent's memory cannot be planned away. Vaultwarden keeps running on the GCP box (Phase 6), loopback :8000 behind its own tunnel, and one monthly pass updates the OS and runs hermes update.

  • Ingress: outbound Cloudflare Tunnel only; Access in front of both the SSH and dashboard routes.
  • Host: A1.Flex 2 OCPU / 12 GB, Ubuntu 24.04; no NSG, ufw deny-inbound, sshd loopback-only, dashboard auth-gated.
  • Workloads: native Hermes (gateway + dashboard) under systemd — no Docker, no browser terminal, no harness.
  • State: six-hourly snapshots to a private OCI bucket via the instance principal; a rebuild restores the newest one at boot, a reset wipes the instance and the snapshots.
  • Rebuild: one workflow run, and CI has no shell on the box.
  • Fleet: the GCP e2-micro stays the Vaultwarden host from Phase 6.
